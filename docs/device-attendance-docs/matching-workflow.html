B · Capture + face matching — the recognition loop

B1 · Capture (camera source)

reader.py runs two threads per camera: a reader at native fps and an analyzer at ≤ 3 fps with motion-skip (skips detection when nothing moved; force_detect_every_s = 3.0 safety net). It emits one detection_events row per new track, not per frame. Detection runs behind a global _detect_lock — serialized across all cameras (the throughput ceiling).

B2 · Matching — how a face becomes an employee

👤Probe face
→
📐512-d embedding
→
📊Cosine vs every enrolled vector
→
ΣMean of top-k (k=1)
→
🎯Highest ≥ 0.45?
  1. The detected face carries a 512-d probe embedding (InsightFace).
  2. Cosine similarity against every enrolled angle vector (both L2-normalized, so dot = cosine).
  3. Per-employee score = mean of the top-k (k = 1) — best angle wins.
  4. Assign the highest scorer only if ≥ MAUGOOD_MATCH_THRESHOLD (0.45). The threshold is hard, never advisory.
  5. Below threshold → employee_id stays NULL = Unknown.

C · Attendance — events into records

The engine is pure — it reads (employee_id, captured_at) events and never knows which source produced them.

  1. Scheduler — every MAUGOOD_ATTENDANCE_RECOMPUTE_MINUTES (default 15). recompute_for(...) handles single employee/date.
  2. Load context — tenant timezone, weekend days, holidays; active employees for today.
  3. Resolve policy — cascade Custom > Ramadan > employee > department > tenant > legacy (one policy per employee/date).
  4. events_for — selects the day's events, converts UTC → tenant local timezone (load-bearing red line).
  5. engine.compute() — pure: in / out / late / early-out / short-hours / overtime / absent, with leave + holiday + weekend handling.
  6. upsert_attendance — ON CONFLICT (tenant_id, employee_id, date). Idempotent, self-healing.

How the device source plugs in

A terminal does its own detection + matching on-device, so it replaces phase B only — phase C is reused unchanged.

Identity mapping = the device's equivalent of matching

The device reports employeeNoString; the device_users table maps it to employee_id (synced in advance by employee code). “The device recognized OM0097” resolves to “employee Anya Kesh”.
