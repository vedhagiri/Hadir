Five tables are involved. Two new registries (attendance_devices, device_users), one new staging queue (device_attendance_events), and two existing tables reused unchanged (detection_events, attendance_records).

1Register the device → attendance_devices

Operator action: Settings → Devices → Add Device. Enter name, host, port, username/password, driver, door number.

Automatically on save, Maugood connects to /ISAPI/System/deviceInfo, reads the serial number + model + firmware, Fernet-encrypts the credentials, and inserts one row.

Why the serial matters: UNIQUE (tenant_id, serial_number) stops the same physical terminal being registered twice and identifies a re-IP'd device as the same unit. The serial is read from the device, never typed.

Audit: device.created — host + serial only, never the password.

2Sync device users → device_users

Operator action: click Sync users (or it runs on schedule). Maugood pulls the terminal's person list and writes each person into a separate table, mapping each to a Maugood employee by employee code (device_user_id == employees.code).

This is the load-bearing table. It is what lets a device event (“person OM0097 seen”) resolve to a Maugood employee (Anya Kesh, employee_id 97). Without a mapped row, the event is unidentified. UNIQUE (tenant_id, device_id, device_user_id) keeps re-syncs idempotent.

Audit: device.users_synced (added / updated / unmapped counts).

3Push enrollment — faces onto the device

The terminal recognizes faces on-device, so each employee's face must live inside the terminal. Maugood takes each mapped employee's reference photo from employee_photos (Fernet-encrypted), decrypts it, and pushes person + face to the device, keyed by employeeNoString = employee code. Then face_synced flips to true.

💡
This is the one extra step cameras don't need. A camera keeps faces in Maugood and matches server-side; a terminal needs the faces loaded into it. On employee delete / PDPL erasure, Maugood also calls delete_person on the device so erasure reaches the terminal.

Audit: device.enrollment_synced.

4Switch attendance source to Device

Operator action: Settings → Attendance Source → choose Device-Based → confirm. Stored as tenant_settings.attendance_source = 'device'.

  • The camera pipeline stops — all capture workers shut down, so the server does no face detection (near-zero CPU).
  • The device pipeline enables — user sync, event ingest, and processing start for this tenant.
ℹ️
Only one mode runs at a time by design (CPU + cost). The switch is reversible and non-destructive — devices, users, and history are kept. Audit: settings.attendance_source_changed.

5Capture events → device_attendance_events

An employee looks at the terminal. It matches them on-board, opens the door, and reports the event by push (real-time webhook POST /api/devices/events) and/or pull (scheduler backstop since the last cursor). Both land in the same staging table.

UNIQUE (tenant_id, device_id, event_serial) is the idempotency key — if the same event arrives by both push and pull, the second insert is a no-op, so nothing double-counts. Times are stored UTC; Omran is UTC+4, so 07:31 local = 03:31Z.

6Process events → detection_events

A processor runs each tick. For every pending (or retry-due) row it resolves device_user_id → device_users.employee_id (OM0097 → 97), inserts one detection_events row with source='device', links it back, marks the staging row processed, and calls recompute_for(employee, date).

Table reused: detection_events — device rows sit beside camera rows in one table (camera_id null, source=device):

Why staging + processing are separate: ingest is fast & idempotent; processing does the mapping + attendance. A mapping problem or transient error retries on the staging row without losing the event.

Data syncing — how, when, and recovery

All syncing runs on one 60-second scheduler tick, gated by attendance_source = 'device' (a camera-mode tenant is skipped entirely).

SyncWhat it doesCadenceIdempotency
User syncPull device person list → upsert device_users + auto-map~15 min + on-demandunique upsert
Enrollment pushPush employee faces → deviceemployee lifecycle + on-demandoverwrites person
Event pullPull events since last_event_cursor → stage60 sunique event_serial
Event pushDevice POSTs to webhook → stagereal-timesame key
ProcessingStaging → detection_events → recompute60 sone event per staged row
🛟
Cursor-based recovery: each device stores last_event_cursor. If Maugood is down or the network drops, the terminal buffers events; the next pull resumes from the cursor and backfills the gap — no events lost. Push + pull = at-least-once; the unique event key makes it effectively exactly-once.
