State 1 — Complete Absence Most common
Employee has an attendance_record with absent=true, no in_time, no pending requests, and all cameras were online during the shift. This is a genuine no-show.
  • Red danger banner clearly states "No attendance recorded" — replaces the current vague message
  • Detection snapshot card shows 0 detections and camera online count — removes "empty space" feel
  • Timeline ribbon stays but shows an explicit "No detections recorded" state instead of just being blank
  • Expected shift tiles give context on what was expected (used by HR when reviewing exception requests)
  • Guidance note explains the two paths available before showing the action buttons
  • Two clear CTAs: Submit exception (valid absence reason) vs Raise escalation (camera miss)
Data source (no new API needed): existing DayDetail fields — evidence, timeline, policy_shift_start, is_holiday

State 2 — Camera Offline / Missed Detection New detection
The system knows from camera_health_snapshots that one or more cameras were unreachable during this employee's shift window. A detection miss is a real possibility. Currently the UI shows a plain "absent" — indistinguishable from a real no-show.
  • Teal "camera-miss" color (distinct from danger-red) immediately signals a technical reason
  • Per-camera status rows show exactly which camera was offline and for how long
  • Timeline ribbon shows the offline window as a red hatched region so the operator sees coverage gaps instantly
  • Coverage % tile (50%) gives a quick quantitative answer: "half the entry points were blind"
  • The escalation CTA is promoted to primary (blue) because the most likely action is to escalate, not submit an excuse
# New field needed on DayDetail + camera_gaps: list[CameraGap] # Each gap = {camera_name, offline_from, offline_to} # Source: camera_health_snapshots WHERE reachable=false # Filtered to the employee's shift window only
How camera gap detection works
  • Query camera_health_snapshots for the tenant, on the employee's shift date
  • Filter snapshots where reachable = false AND captured_at is within the shift window
  • Group by camera, produce (offline_from, offline_to) intervals
  • If any gap overlaps the shift window → show State 2 instead of plain absent
  • Show at most 3 cameras in the drawer (most relevant to the employee's building zone)

State 3 — Low Confidence Detection Amber state
detection_events rows exist for this employee on this day, but all have confidence < MAUGOOD_MATCH_THRESHOLD (default 0.45). The system decided not to count them as confirmed presence. This is meaningfully different from a complete absence — the employee may have been there.
  • Amber "face unclear" badge replaces the plain red "Absent" — immediately signals a partial detection
  • Detection snapshot shows best match score vs threshold — HR can see exactly how close it was
  • Low-confidence face crops are shown with confidence % badges — HR can visually confirm or deny
  • Timeline dots (amber) appear at detection times — not the solid blue bars of confirmed presence
  • "Update reference photo" action is promoted — this is the long-term fix for chronic low-confidence

State 4 — Request Pending New sub-state
The employee has already submitted an escalation or exception request for this absent day. Currently the drawer shows nothing about this — the employee has no way to see the status without navigating to the Approvals page. This state fills that gap.
  • Purple "Under review" badge replaces the alarming red "Absent" — the situation is in hand
  • 4-step progress tracker gives the employee a clear picture of where they are in the flow
  • Request summary card shows reason, comment excerpt, and who it's currently assigned to
  • Actions change from "submit" to "view" / "cancel" — no duplicate submissions possible
  • Escalation and exception requests are both shown this way — the progress steps are identical

State 5 — Exception / Leave Approved Resolved
The attendance record's absence has been authorised through the approval workflow. This is different from the escalation-confirmed "present" state (State 5 of the original workflow) — here the employee was genuinely absent, but the absence is approved. The distinction: escalation changes absent→present; exception acknowledges the absence.
  • Green "Absence approved" badge replaces alarming red — the situation is resolved
  • Full approval chain with names, timestamps, and comments is shown inline
  • Distinction between exception (valid reason) and leave (deducted from balance) is shown clearly
  • No escalation or exception buttons shown — the day is settled, actions would be inappropriate
  • A single "View history" link gives access to the complete audit trail
Uses existing fields: escalation_request model is extended to cover both exception and escalation approvals — or a new approved_request field is added. See backend delta below.
All 5 states — decision tree
// DayDetailDrawer absent-state selector (frontend) if (detail.escalation_confirmed) → EscalationConfirmedCard (present) else if (detail.approved_request) → State 5 – Approved absence else if (detail.pending_request) → State 4 – Request in progress else if (evidence.length > 0) → State 3 – Low confidence else if (camera_gaps.length > 0) → State 2 – Camera offline else → State 1 – Complete absence
